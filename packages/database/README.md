# Database workspace (M00 draft)

Prisma 7.10.1 CLI, client and PostgreSQL adapter are pinned to a documented v7 release; pg 8.23.1 is the candidate driver. Registry resolution, transitive lockfile, schema validation, generated client, typecheck and actual migration have not been run. Do not run commands against a hosted database. Supabase CLI owns infrastructure/platform schemas; Prisma owns app tables. No domain model or real data is introduced.

## Local setup gate

1. Confirm local prerequisites, start the local Supabase CLI, inspect the actual ports and verify no remote Docker context. Provision a restricted runtime login and distinct migration login using local administrative tooling; give migration login ownership of the private construct_ai schema, not broad superuser access. Create a dedicated empty database named construct_ai_shadow on the same local instance, owned by the migration login. It must contain no application or personal data: Prisma migrate dev may reset it. Never point the shadow URL at the app database.
2. Populate gitignored root .env with DATABASE_URL (runtime), DATABASE_MIGRATION_URL (migration), DATABASE_SHADOW_URL (dedicated shadow, migration login). Both app URLs must point to the same local DB/port. Use percent-encoded credentials; never paste keys in public logs. Keep migration/shadow credentials out of long-lived runtime processes. The guard validates names/targets, not actual PostgreSQL role privileges.
3. Install verified dependencies and generate the real lockfile. Run pnpm local:config; run pnpm db:validate and pnpm db:generate. Confirm Prisma version compatibility and generated client; fix any issues before proceeding.
4. Use the installed CLI help for migrate dev. Generate the initial migration with --create-only, review SQL and scope before applying locally, never accept a reset prompt without explicit approval. Review grants and RLS as applicable. Enable pgvector locally and verify extension and vector operations; do not invent migration history. Commit actual migration artifacts only after execution and review. No dual ownership with Supabase migration history.
5. Grant runtime USAGE on construct_ai and only required SELECT/INSERT/DELETE on the foundation_probe table (no DDL, no migration role membership, no browser access). Confirm no exposed Data API schema or PUBLIC/anon/authenticated grants; review inherited privileges. Foundation probe contains no tenant data. Tenant models and tenant RLS/authorization begin in M01.
6. Run pnpm db:check against runtime credentials, pnpm --filter @construct-ai/database build, pnpm db:smoke. The synthetic probe creates/reads/deletes a random UUID in one transaction. No residual row on success; failures should roll back. Verify actual database query and logs. The smoke is not a full tenant-security test.

The database package is server-only, and not yet wired into API readiness. Root environment loading is for local CLI convenience; never ship migration secrets to frontend or service runtime. Generated files and migrations are distinct: ignore generated client source; commit reviewed migration history and lockfile.
